# 个人知识库：当前方案与实施路线

> 文档状态：当前唯一生效方案。
>
> 实现基线：`feature/knowledge-spine` 分支，知识脊柱 Gate 已在 `6be9561` 完成。
>
> 适用范围：个人知识库后续的 P1 / P2 / P3。早期分析文档只保留问题背景，不再承担排期和实现定义。
>
> 方案审查：P1 已完成设计审查，可以进入测试先行的实施；P2、P3 目前只定义边界，进入实现前必须分别补充设计与验收标准。

---

## 1. 为什么需要一份新方案

项目目前已经有一条可靠的数据脊柱，但还没有一份基于当前代码事实、可直接执行的个人知识库计划。

旧文档中的“P1”分别指过高价值视图、embedding、方向反馈，继续并行使用会造成三类问题：

1. 同一个阶段名称对应不同目标，无法判断先做什么；
2. 早期分析描述的是知识脊柱实施前的数据结构，部分事实已经过期；
3. 容易从新表、新算法或 UI 功能开始，而不是先改善用户每天看到的知识列表。

因此，从本文档开始只保留一条实施路线：

1. **P1：高价值知识视图**——先让已有知识更容易被找到和判断；
2. **P2：学习生命周期与成长**——再让知识从收录走向掌握；
3. **P3：关联、方向反馈与语义能力**——最后建立扩展和自我校准能力。

发布版本号由 `ROADMAP.md` 安排，本文档只定义产品与工程顺序。

## 2. 产品目标与非目标

### 2.1 产品目标

保持现有的主工作流不变：

```text
截图 → OCR / AI 解释 → 术语与学习建议 → 本地沉淀
```

个人知识库要在这条工作流上增加三个结果：

- 用户能快速看到“对我重要、与当前方向相关”的知识，而不是被基础词和时间顺序淹没；
- 每个判断都有来源和理由，可以回到原截图验证；
- 后续能够沿着同一数据入口增加学习生命周期、成长统计和知识关联。

### 2.2 非目标

当前路线不把产品扩成通用笔记工具或图谱编辑器，不建设：

- 自由页面、文件夹、双链笔记和块编辑器；
- 通用事件总线或通用数据中台；
- 为了“以后可能用到”而提前新增的评分表、关系表和缓存表；
- 静默改写学习方向或用户画像的自动代理；
- 大规模 UI 重设计。

## 3. 当前事实基线

知识脊柱已经提供以下可靠事实：

| 事实 | 当前落点 | 可支持的能力 |
|---|---|---|
| 术语及其领域 | `terms` | 展示、搜索、收藏、复习 |
| 术语的真实来源 | `term_captures` | 来源数量、回看截图、共现计算 |
| 截图发生时的方向 | `captures.context_id` | 当前方向精确匹配 |
| 可读领域快照 | `terms.domain` / `captures.domain` | 旧数据和无具体方向时的回退 |
| 用户主动信号 | `favorite`、`user_edited`、`views` | 判断显式意图 |
| 出现与复习事实 | `occurrences`、`review_events`、SRS 字段 | 证据强度与学习状态 |
| 学习建议及状态 | `learning_tips` | 后续建议转知识、成长统计 |
| 统一知识入口 | `KnowledgeBase` | 隐藏去重、回链、调度和底层存取 |

当前缺口不是“没有数据”，而是查询仍然过浅：

- `focus` 只折叠没有行为信号的 `basic` 词；
- 列表仍按出现次数和首次时间排序；
- UI 为一次刷新分别调用领域计数、总数和列表，并直接知道底层过滤参数；
- `context_id` 已经记录，但没有用于术语视图；
- 用户只能看到结果，看不到“为什么它排在这里”。

因此，P1 不需要再迁移数据，也不需要引入 embedding。

## 4. 统一概念

为避免后续再次把不同问题混成一个总分，固定以下术语：

### 4.1 知识价值

用于知识库浏览，回答：

> 这个词对当前用户、当前方向是否值得优先看到？

它主要由用户显式意图、方向相关性和来源证据决定。

### 4.2 学习优先级

用于复习与学习队列，回答：

> 这个词现在是否需要学习或复习？

它由到期时间、复习结果、遗忘次数和学习状态决定。

**两者不能共用一个排序。** 收藏但与当前方向无关的词仍有知识价值；频繁遗忘的词学习优先级很高，但不一定是当前方向最核心的知识。

### 4.3 来源证据

一个术语连接到多少条不同的 capture，以及这些 capture 属于什么方向。来源数量必须按不同 `capture_id` 计算，不能用重试次数或简单写入次数代替。

### 4.4 当前方向

由调用方传入：

- `current_context_id`：当前具体学习方向，可空；
- `effective_domain`：当前可读领域，作为旧数据和无具体方向时的回退。

`KnowledgeBase` 不读取 UI 设置，也不依赖 `SettingsService`。

---

## 5. 总体设计原则

1. **保存事实，派生判断。** 继续保存来源、方向和行为；不保存 `score`。
2. **先规则分层，再考虑权重模型。** 可解释、可测试的规则足够解决当前几百个术语的噪声问题。
3. **一个用例，一个接口结果。** UI 请求一页术语时，不再自己拼接列表、总数和领域统计。
4. **搜索优先于折叠。** 用户主动搜索时，匹配的基础词也必须可见。
5. **旧数据诚实回退。** `context_id IS NULL` 只用领域判断，不伪造具体方向。
6. **复习排序保持不变。** P1 不改变 SRS、收藏语义、复习到期规则和 digest。
7. **索引由证据驱动。** 先用现有索引和聚合查询；只有查询计划或基准证明需要时才加索引。

## 6. P1：高价值知识视图

### 6.1 目标

用现有事实建立三个稳定视图：

| 视图 | 用途 | 是否隐藏无信号基础词 | 方向规则 |
|---|---|---:|---|
| `focus`（重点） | 默认浏览整个知识库 | 是 | 当前方向相关项优先，但不限制范围 |
| `current_direction`（当前方向） | 只看正在学习的方向 | 是 | 精确 context 命中；旧数据按 domain 回退 |
| `all`（全部） | 完整查找与治理 | 否 | 不按方向过滤，可保留领域筛选 |

默认视图为 `focus`，延续当前“默认折叠基础词”的体验，只改变排序质量并增加解释。

### 6.2 P1 不做什么

P1 明确不修改：

- 数据库 schema；
- 收藏自动进入复习的现有行为；
- SRS 到期队列顺序；
- 术语生命周期状态；
- digest 输入；
- learning tip 类型；
- embedding 和语义检索；
- 主表、多义项或 `term_pairs` 重构。

这样可以把风险集中在“只读查询 + 小范围 UI 消费”这一个接缝上。

### 6.3 统一查询接口

在现有 `KnowledgeBase` 内加深查询能力，不新建 `KnowledgeQueryService`、Repository 或评分服务。

接口概念如下，名称可在实现时按项目风格微调：

```python
@dataclass(slots=True)
class TermQuery:
    view: str = "focus"  # focus | current_direction | all
    query: str = ""
    domain: str = ""
    current_context_id: int | None = None
    effective_domain: str = "通用"
    limit: int = 50
    offset: int = 0

@dataclass(slots=True)
class TermViewItem:
    term: TermRecord
    source_count: int
    current_context_source_count: int
    direction_level: str  # exact | domain | none
    rank_tier: str
    reasons: tuple[str, ...]

@dataclass(slots=True)
class TermPage:
    items: list[TermViewItem]
    total: int
    domain_counts: list[tuple[str, int]]

class KnowledgeBase:
    def query_terms(self, query: TermQuery) -> TermPage: ...
```

这个接口负责一个完整的“刷新术语页”用例：

- UI 不再分别读取 `HistoryStore.list_terms`、`count_terms` 和 `term_domain_counts`；
- 过滤、排序、计数使用同一份查询语义，避免三个结果不一致；
- `total` 和 `items` 应用当前领域筛选；`domain_counts` 应用相同视图和搜索条件，但在领域筛选前统计，保证筛选菜单仍可切换；
- 排序理由随结果返回，UI 不重复推导业务规则；
- `HistoryStore` 仍只负责 SQL 与行映射。

P1 完成后，旧的 `KnowledgeBase.list_terms/count_terms/term_domain_counts` 可先保留给非 UI 调用；没有调用者后再删除，不建立长期双路径。

### 6.4 基础词过滤规则

基础词不再只按“出现次数”判断价值。

`focus` 和 `current_direction` 中，满足以下任一显式信号的基础词可以重新出现：

- 已收藏；
- 用户编辑过；
- 用户主动查看过。

没有显式信号的 `basic` 词无论出现多少次都不进入重点视图。用户主动搜索时不应用这条隐藏规则，确保任何词都能被找到。

这能避免 `file`、`data` 一类词因每张截图都出现而挤占前排，同时保留用户主动关注基础概念的能力。

### 6.5 方向相关性规则

方向判断按证据强弱分三级：

1. `exact`：至少一条来源 capture 的 `context_id` 等于当前 `current_context_id`；
2. `domain`：术语领域等于 `effective_domain`；
3. `none`：没有当前方向证据。

`current_direction` 视图的范围规则：

- 有 `current_context_id` 时，纳入 `exact` 项；
- 对只有旧来源（关联 capture 的 `context_id` 全为 `NULL`）或没有来源的手工术语，允许用相同 domain 回退；
- 已经有其他非空 context 来源、但不属于当前 context 的术语，不能仅凭同 domain 冒充当前具体方向；
- 没有 `current_context_id` 时，只按 `effective_domain` 过滤。

现有手动领域筛选在 `focus` / `all` 中继续可用；进入 `current_direction` 时由方向范围接管，避免两个筛选器给出冲突含义。

### 6.6 排序：可解释分层，不使用黑盒总分

P1 使用稳定的分层排序键，不持久化分数：

```text
第一层：用户显式意图
  收藏 / 用户编辑 > 无显式意图

第二层：方向相关性
  当前 context 精确来源 > 同领域回退 > 无方向证据

第三层：来源与行为证据
  不同来源数量（封顶） > 查看次数（封顶） > 最近来源时间

最终稳定键
  term.id
```

“封顶”表示高频只证明“多次出现”，不能无限放大价值。例如来源数超过 5 条后不再继续提高排序档位；查看次数超过 3 次后也不继续增加优势。具体封顶值作为常量并由排序测试固定，不进入数据库。

说明：

- 基础词惩罚已经通过可见性规则完成，不再叠加难以解释的负权重；
- `lapses`、`due_at` 不参与知识价值排序，它们属于学习优先级；
- 搜索结果仍使用同一稳定排序，但不隐藏基础词；
- 如果真实数据证明分层不足，再以用户标注样本讨论权重模型，而不是预先引入公式。

### 6.7 排序理由

每项最多返回 3 条最有解释力的理由，例如：

- `用户已收藏`
- `用户编辑过解释`
- `当前方向出现 3 次`
- `与当前方向同领域`
- `来自 5 条学习记录`
- `用户查看过`

理由由 `KnowledgeBase` 生成，UI 只展示。P1 可以先放在术语详情区，不新增表格列，避免压缩当前列表。

### 6.8 数据查询策略

底层查询以 `terms` 为主表，聚合：

- `COUNT(DISTINCT term_captures.capture_id)`；
- 当前 context 的来源数量；
- 来源中最新的 `captures.created_at`；
- 是否存在非空且不属于当前 context 的来源。

要求：

- 一个页面请求不允许逐术语查询来源，禁止 N+1；
- 列表和分页必须有完整稳定排序键；
- 计数与列表共用相同过滤构造，不能复制三套 `WHERE`；
- 先使用现有 `term_captures` 主键、反向索引和 `idx_captures_context`；
- 新增索引前必须给出 `EXPLAIN QUERY PLAN` 或基准证据。

### 6.9 UI 最小调整

只增加必要的消费能力：

1. 术语页增加“重点 / 当前方向 / 全部”视图切换；
2. 默认选择“重点”；
3. “当前方向”视图显示当前方向名称；没有可用方向时退化为当前领域；
4. 术语详情区显示排序理由和来源数量；
5. 保留现有搜索、领域筛选、分页、收藏、复习和出处跳转；
6. 不改变表格视觉结构，不做新的知识库首页。

### 6.10 P1 实施顺序

#### A. 查询契约与失败测试

- 定义三个视图和方向回退规则；
- 建立小型排序 fixture，覆盖基础词、用户意图、精确方向、旧数据和分页；
- 先写接口级失败测试，再改 SQL。

#### B. 查询实现

- 在 `HistoryStore` 内实现一次聚合查询及共享过滤构造；
- 在 `KnowledgeBase.query_terms` 内完成视图规则、排序理由和完整结果拼装；
- 保持现有写入、复习和 ingest 路径不变。

#### C. UI 接线

- `MainWindow.refresh_terms` 只调用一次 `KnowledgeBase.query_terms`；
- 增加视图状态和最小控件；
- 显示理由，不在 UI 重算排序。

#### D. 验收与清理

- 运行排序契约测试、知识脊柱回归测试和相关 UI 测试；
- 用真实数据库副本检查查询结果和性能；
- 完成桌面 smoke；
- 确认 UI 不再直接调用 `HistoryStore` 的术语列表/计数方法；
- 删除已无调用的重复查询路径。

### 6.11 P1 验收标准

#### 数据与规则

- `all` 能返回所有匹配术语，不因基础词规则漏项；
- 搜索能找到无行为信号的基础词；
- 无行为信号的基础词不会因高频进入 `focus`；
- 收藏、用户编辑或查看过的基础词能进入 `focus`；
- 当前 context 精确命中的术语排在仅同领域术语之前；
- 旧 `context_id = NULL` 数据只按规定进行领域回退；
- 来源数按不同 capture 计算，同 capture 重试不改变排名；
- 分页顺序稳定，无重复、无跳项。

#### 架构与复杂度

- 不新增表和持久化 score；
- 不新增并行服务层；
- UI 一次刷新只依赖一个知识查询用例；
- UI 不知道基础词可见性和方向回退的底层条件；
- SRS、收藏写入、ingest 和 digest 行为无变化。

#### 性能与体验

- 查询无 N+1；
- 在真实数据库副本上记录 P1 前后查询耗时；
- 以 1,000 个术语、10,000 条来源链接的 fixture 做基准，普通开发机单页查询目标小于 100 ms；
- 用户能从每个重点结果看到至少一条可理解的排序理由；
- 完成桌面真实渲染 smoke，不只依赖控件测试。

## 7. P2：学习生命周期与成长

P2 的目标是让“见过”逐步变成“掌握”，但不在 P1 中提前加入状态迁移。

候选范围：

- 收藏与“加入学习”语义拆分；
- 明确 `new / learning / mastered / archived` 的进入和退出条件；
- 复习失败回炉并回看来源；
- 由 `review_events` 计算周新增、复习完成率、遗忘和掌握趋势；
- digest 使用新增记录、已掌握术语和已完成建议，而不是只吃解释文本。

P2 实施前必须单独确认：

1. 现有收藏用户如何迁移到学习池；
2. “掌握”的判定阈值及允许用户手动覆盖的方式；
3. 归档是否影响搜索、复习和统计；
4. digest 游标和方向范围；
5. 状态迁移与 `review_events` 的一致性不变量。

在这些问题通过设计审查前，不新增生命周期字段或迁移现有状态。

---

## 8. P3：关联、方向反馈与语义能力

P3 在结构化事实已足够使用后再扩展：

1. 先从 `term_captures` 动态计算同 capture 共现；
2. 学习建议结构化，并支持转为待学术语候选；
3. 记录用户对方向识别的确认、纠正和切换反馈；
4. 只有关键词、来源和共现无法满足检索时，再接 embedding；
5. 只有动态共现查询被规模证明过慢时，再考虑物化 `term_pairs`。

embedding 属于检索增强手段，不是个人知识库 P1，也不自动等于知识关系。

## 9. 明确延后

以下工作没有被取消，但不能提前阻塞 P1：

- term 主表、多义项和规范化重构；
- 通用行为事件模型；
- 物化知识图谱；
- 自动生成和改写方向画像；
- 跨设备同步；
- 通用笔记能力；
- UI 全面重构。

已发现的历史 `conversations` 孤儿记录属于删除流程的数据完整性问题，应作为独立可靠性修复处理；它不参与知识排序，也不应借 P1 顺手扩大为全库清理。

### P1：通过

- 完全建立在已完成的知识脊柱事实之上；
- 不需要 schema 迁移，也不改变现有写入和复习语义；
- 只加深现有 `KnowledgeBase`，没有新增平行抽象；
- 把 UI 的三次底层查询收敛成一个用例，复杂度净减少；
- 用可解释分层替代持久化总分，规则可被小型 fixture 穷举验证；
- 对旧 `context_id = NULL` 数据有明确、诚实的回退策略。

### P2 / P3：方向通过，尚未达到实施 Gate

它们的产品顺序和禁止项已经明确，但涉及状态迁移、摘要输入、反馈数据和可能的新 schema。开始实施前必须各自形成独立设计、迁移方案和验收标准，不能直接照候选清单编码。
